## Context

См. `proposal.md` и `specs/ios-quick-capture/spec.md`. Проект пока содержит только исторический план. У целевого iPhone нет Action Button. Модель устройства и версия iOS неизвестны, поэтому первый результат разработки — измеренный технический прототип на этом устройстве, а не обещание поведения по документации. На текущем Mac `xcodebuild` не запускается: выбран `/Library/Developer/CommandLineTools`, а Xcode не обнаружена в стандартных папках. Перед сборкой нужно найти или установить полную Xcode и выбрать её как active developer directory.

## Goals / Non-Goals

**Goals:**
- Проверить полный путь от кнопки на экране блокировки до локально сохранённой операции при отключённой сети.
- Сделать минимальный клиент, пригодный для короткого личного теста, если технический прототип подтверждает путь.
- Отделить факты, наблюдаемые на устройстве, от предположений об iOS.
- Сделать сборку воспроизводимой: структура targets, разрешения, подпись, установка и проверка на физическом устройстве описаны явно.

**Non-Goals:**
- Общий аккаунт, сервер, синхронизация, Telegram и веб-кабинет.
- Большая система категорий, автоматическая банковская загрузка и AI-анализ.
- Обещание одинаковой поддержки всех моделей iPhone до тестирования.

## Decisions

### 1. Начать с проверки на целевом устройстве

До выбора API зафиксировать модель iPhone, версию iOS и выданные разрешения. Для WidgetKit Control нужна iOS 18 или новее. Для iOS 26+ проверить `SpeechTranscriber` и затем `DictationTranscriber` при ограничении языка/устройства; для iOS 18–25 проверить `SFSpeechRecognizer(ru-RU)` только с `supportsOnDeviceRecognition == true` и `requiresOnDeviceRecognition == true`. Если установленная iOS не поддерживает кнопку или русское офлайн-распознавание на конкретном iPhone недоступно, исходная гипотеза не подтверждена. Альтернатива — начать с обычного экрана приложения — быстрее для кода, но не отвечает на главный вопрос.

### 2. Одна нативная кодовая база для прототипа

Один Xcode-проект с основным SwiftUI app target, Widget Extension для `ControlWidgetButton`, общим определением App Intent и test target. Widget Extension только показывает кнопку и передаёт действие; микрофон, парсер и SwiftData находятся в процессе приложения. Сначала проверить App Intent, который начинает запись без открытия UI. Для `AudioRecordingIntent` держать Live Activity активной всё время записи, если этот путь применим на целевом устройстве. Если iOS переводит действие в foreground или требует разблокировку, измерить этот путь отдельно. `OpenIntent`, открывающий экран записи, допускается как диагностический fallback и не подтверждает обещание «без открытия приложения». В кнопке и Live Activity не показывать сумму, описание и распознанный текст на заблокированном экране.

Ожидаемая структура после создания проекта:

```text
FinanceBro.xcodeproj
FinanceBroApp/             SwiftUI App, onboarding, CaptureView, TransactionsView
FinanceBroCore/            CaptureCoordinator, SpeechService, TransactionParser,
                           TransactionStore, Transaction model, CaptureMetrics
FinanceBroControls/        WidgetBundle, QuickCaptureControl, Live Activity view
FinanceBroShared/          StartCaptureIntent и общие типы для app/widget targets
FinanceBroTests/           parser и модель денежных сумм
```

Общий intent включается в нужные targets согласно проверенному варианту выполнения; владение записью остаётся у app target. Структура папок — ориентир, а не требование к конкретным именам Swift-типов.

### 3. Распознавание строго на устройстве

В `SpeechService` отделить захват аудио от движка распознавания, чтобы менять API без изменения UI и парсера. `CaptureCoordinator` управляет стадиями `idle → recording → transcribing → parsing → saving → success/error`; повторный тап не создаёт вторую запись. Для `SpeechAnalyzer` проверить `supportedLocales`, `installedLocales` и статус asset; при необходимости один раз загрузить модель во время настройки. Для старого Speech API принудительно включить локальное распознавание и проверить `ru-RU` при отключённой сети. В app target указать `NSMicrophoneUsageDescription` и запросить доступ к микрофону при первичной настройке; если применяется `SFSpeechRecognizer`, также добавить `NSSpeechRecognitionUsageDescription` и запросить доступ к распознаванию. Для Live Activity добавить `NSSupportsLiveActivities` и минимальное представление в Widget Extension. Сырой аудиофайл не сохранять после завершения попытки; исходный текст сохранять в операции. Альтернатива — серверное STT — не проверяет офлайн-гипотезу.

### 4. Минимальная локальная модель

Запись: UUID, тип (`expense`/`income`), сумма в копейках как целое число, валюта (в MVP RUB), дата операции, описание, исходный текст (для ручного ввода может отсутствовать), источник (`voice`/`manual`), время создания и изменения. Использовать SwiftData в app target; Widget Extension не открывает базу. Сохранение считается успешным после явного `ModelContext.save()`, затем выдаётся краткий сигнал. Автосохранение SwiftData не используется как критерий подтверждения операции. Не включать CloudKit и App Group без фактической нужды. Альтернатива — серверная БД — создаёт ненужную зависимость от сети.

### 5. Ограниченный локальный парсер

Правила разбирают одну числовую сумму (`480`, `50 000`, `480,50`), явные маркеры дохода (`получил`, `зарплата`) и расхода (`потратил`, `купил`), а также несколько однозначных слов расходов (`кофе`, `такси`, `продукты`). Дата по умолчанию — момент записи; «вчера» обрабатывается только после основных случаев. При нескольких суммах или неопределённом типе операция открывается для исправления до сохранения. Сложные числительные и умная категоризация остаются за пределами первой версии. Альтернатива — LLM-парсер — добавляет задержку и сетевую зависимость.

### 6. Полевой тест без сервера аналитики

Локально собирать лишь тайминги, способ запуска, код стадии ошибки и признак исправления. Суммы и аудио не включать в диагностические события. Пользователь отдельно отмечает, сколько реальных операций не записал, чтобы оценить полноту. Рабочие критерии проверки: медиана от нажатия до сохранения не более 5 секунд, не менее 80% голосовых записей без исправления суммы/типа и регулярное использование в течение первой недели. Если подпись позволяет, продлить наблюдение до 10–14 дней. Это пороги для решения по MVP, не гарантии производительности.

### 7. Локальная сборка, установка и первичная настройка

1. Установить полную Xcode с SDK для целевой iOS; выбрать её как active developer directory и проверить `xcodebuild -version`. Command Line Tools недостаточно для сборки iOS-приложения и запуска на устройстве.
2. В Xcode добавить Apple Account, включить automatic signing для app и Widget Extension, назначить один team и уникальные bundle identifiers. Проверить доступность требуемых capabilities для выбранной команды подписи, прежде чем писать зависимый от них код.
3. Подключить iPhone к Mac, подтвердить доверие, выбрать его как run destination. При запросе включить Developer Mode на iPhone. Запустить app scheme: Xcode подпишет и установит приложение вместе с extension. Не хранить Apple ID, сертификаты и provisioning profiles в проекте.
4. Открыть приложение на iPhone, выдать разрешение микрофона и, только при использовании старого Speech API, разрешение распознавания речи. При подключённой сети проверить/загрузить модель русского языка. Показать состояние «готово к офлайн-вводу» только после успешной проверки.
5. Добавить Control в настройке экрана блокировки, заблокировать телефон, включить авиарежим и пройти реальный сценарий. Повторить после перезапуска iPhone и приложения. Снять поэтапные тайминги: тап → старт записи → финальный текст → сохранение.

Локальная установка через Xcode — путь первой проверки на одном iPhone. С бесплатной Personal Team provisioning profile действует 7 дней: для более длинного теста потребуется повторная подпись и установка без удаления локальных данных; сохранность данных проверить заранее. Распространение нескольким людям через TestFlight требует отдельного решения о программе разработчика и не входит в этот change.

### 8. Проверка результата и решение о продолжении

Сначала сделать минимальный вертикальный прототип `Control → App Intent → microphone → text` на физическом устройстве, затем добавить `parser → SwiftData → confirmation`. Симулятор подходит для проверки UI и парсера, но не доказывает работу заблокированного физического iPhone. Отчёт фиксирует модель/версию iOS, способ подписи, шаги пользователя, результаты в авиарежиме, задержки и ошибки. Если запуск без разблокировки или русское офлайн-распознавание не работают, продолжение полноценного MVP требует отдельного решения о смене входного сценария; переход к ручному вводу не считается успешной проверкой голосовой гипотезы.

## Risks / Trade-offs

- [Кнопка или запись требуют разблокировки] → проверить первой на целевом устройстве; зафиксировать число шагов и пересмотреть обещание продукта до расширения MVP.
- [Русская офлайн-модель не поддерживается или не установлена] → проверить API и авиарежим; дать ручной ввод, но не считать голосовую гипотезу подтверждённой.
- [Запуск или распознавание медленнее ожидаемого] → замерять этапы отдельно; упрощать UX только после нахождения узкого места.
- [Ошибки распознавания финансовых сумм] → после разблокировки показывать записанную сумму и давать быстрое исправление; на экране блокировки оставлять только нейтральное подтверждение.
- [Измерение пропущенных трат неточно] → сочетать локальные тайминги с коротким ежедневным самоотчётом пользователя.
- [На Mac нет полной Xcode] → установить Xcode перед сборкой; подтвердить рабочую версию и iOS SDK командой `xcodebuild -version`.
- [Подпись или capabilities не проходят с выбранным Apple Account] → проверить установку пустого app и Widget Extension на целевой iPhone до реализации речи и хранения.
- [Бесплатная подпись истекает во время теста] → начать с 7-дневного пилота; при продлении повторно подписать и установить сборку без удаления данных, затем проверить их сохранность.

## Migration Plan

Новой системы пока нет. Создать минимальный iOS-проект для технического прототипа, подписать и установить его локально. После положительного результата расширить ту же сборку до MVP и провести личный тест. При отрицательном результате прототипа сохранить отчёт и не продолжать реализацию полного MVP до пересмотра сценария запуска.
